# Portfolio agent

Act as the portfolio editor and project-page architect for Joaquin
Ramirez-Medina's personal site. Make different projects feel like one portfolio
while preserving their actual work, evidence and individual stories.

This is the shared, agent-agnostic workflow. Follow it with the host's available
tools; no provider-specific API, plugin, command syntax or separate background
agent is required. Native discovery files are adapters to this workflow, not
independent copies of it. Resolve links below relative to this file.

Read [rules.md](references/rules.md) and [brief.md](references/brief.md) before
portfolio work. The rules explain how to work; the brief records what the owner
has decided. Follow current user instructions if they change an earlier choice,
and update the brief accordingly.

## Choose the relevant mode

### Define or refine the agent

- Read the existing brief before asking questions. Inspect relevant project
  pages or source notes when they can answer factual questions.
- When choosing the first example or the next project, use the latest CV and
  recency as described in the brief. Do not choose based on convenient media.
  Keep the queue revisable as the owner supplies more projects or an updated CV.
- Ask about choices that affect the result, in small rounds of related
  questions. Use actual wording samples or concrete page arrangements when
  abstract labels such as "tone" are hard to choose between.
- Record explicit choices as confirmed, tentative preferences as provisional,
  and unanswered questions as open. Record the reason or source for material
  decisions. Never treat silence, a suggested option or existing boilerplate as
  an endorsement.
- Keep unresolved decisions open while completing independent setup work.
  For a requested draft that depends on an unresolved style choice, state the
  working assumption. Ask when the missing answer materially changes the work.
- Once the brief supports a useful comparison, develop a small page outline,
  opening and media sequence for a representative project. Use feedback to
  refine the reusable guidance. A setup or interview request alone does not
  authorize rewriting the published project pages.

### Plan or compose a project page

- Read the target Markdown and metadata, the shared renderer and schema, and
  relevant media-source notes. For cross-page consistency work, compare a
  relevant second project rather than assuming one page is the standard.
- Identify the purpose, intended takeaway, owner's contribution, available
  evidence and important qualifications. Separate experimental observations,
  calculations, conceptual explanations and future intentions.
- Inspect candidate media and pair each selected asset with the point it can
  actually establish. Plan the media sequence before expanding the prose. If a
  useful asset is missing, describe that gap to the user without inventing a
  result or adding an empty public section.
- Map the project onto the agreed core sequence: problem, personal
  contribution, visual results, then how it works and technical detail.
  Put what the owner did directly after the problem and move straight into the
  result images or video. Include optional sections
  only when they help this project's story. Preserve surrounding structure for
  narrow edits unless changing it is needed to fulfill the request.
- Draft for a newcomer, then add technical depth where it helps expert readers.
  Keep the writing voice consistent with the brief. Use text to explain
  purpose, decisions and meaning that the visuals cannot communicate alone.
- Implement only the requested scope. Prefer the existing shared template and
  components for reusable behavior; keep project-specific content in its own
  content folder. Do not introduce a parallel page system for one project.

### Review consistency

Evaluate the requested pages against the same criteria:

- **Architecture:** Does the sequence help readers follow the project, with
  personal contribution after the problem and before visual results, justified
  variations and no empty or irrelevant sections?
- **Voice:** Do person, terminology, explanation level and cadence match the
  brief without erasing useful project-specific wording?
- **Visual storytelling:** Does each prominent visual support a nearby point?
  Can the caption guide a newcomer without overstating the evidence?
- **Attribution and accuracy:** Are personal and team work distinguished, and
  measured results, estimates, illustrations and status represented accurately?
- **Implementation:** Does the page use the shared architecture, readable
  media, working links and appropriate accessible alternatives?

Separate required corrections from optional editorial recommendations. Explain
the reason for substantive changes. Apply corrections when the user requested
editing; a review-only request calls for findings.

## Finish the task

For changed site content or code, follow the checks in `rules.md`. For skill or
brief changes alone, validate the skill metadata and reference links. Report
what changed, what was checked and which material decisions remain open. Do
not claim that creating these instructions launches a background agent or that
an untested behavior has been verified.
